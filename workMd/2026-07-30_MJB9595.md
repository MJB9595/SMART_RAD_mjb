## 1. 작업 목적

권한 관리(RBAC) 화면에서 역할의 권한을 바꿔도 아무 변화가 없다는 제보에서 출발했다. 원인을 추적한 결과 **`role` / `permission` / `role_permission` / `employee_role` 4개 테이블이 화면 표시용으로만 존재하고 실제 인가에는 전혀 쓰이지 않고 있었다.** 인가는 `employee.role` 열거값(ADMIN/HR/EMPLOYEE) 하나에만 의존했다.

이를 바로잡는 과정에서 권한 경계가 무너진 지점들이 연쇄적으로 드러나 함께 처리했다.

- RBAC를 인증·인가 경로에 실제로 연결 (권한 변경이 즉시 반영)
- 역할 비활성화 시 해당 계정 접근 차단
- 신청 API의 대리 신청 취약점 및 타인 개인정보(급여·경조사·증명서 사유) 노출 차단
- 화면에 남아 있던 임의 생성 데이터·죽은 버튼·미구현 기능 정리

### 2-2. 대상 교직원 선택 API 신설 (`36a807e`)

`GET /employees` 가 ADMIN·HR 전용이라 일반 직원은 403을 받았고, 화면은 `.catch(() => [])` 로 삼켜 선택 상자가 빈 채로 남았다. 근태·휴가는 `AuthUser`를 `Employee`로 캐스팅해 `option value`가 `undefined`였다.

```
GET /employees/selectable    (isAuthenticated)
→ [{ id, employeeNumber, name, departmentName, positionName, self }]
```

범위는 **서버가 결정**한다. ADMIN → 전원 / HR → 관리자 제외 전원 / 그 외 → 본인만.

## 3. 처리 기준 / 비즈니스 로직

### 3-1. 역할 비활성화 차단
- 역할을 배정받았는데 **전부 비활성**이면 로그인·기존 토큰 모두 403 + `비활성된 계정 / 권한 입니다. 관리자에게 문의해주세요.`
- **배정이 아예 없는 계정은 차단하지 않는다.** 차단하면 백필 이전 계정·신규 승인 계정이 로그인 불가가 되기 때문. 이 경우 열거값으로 최소 권한만 부여한다.
- `ROLE_ADMIN`은 수정·비활성·삭제 불가(`PROTECTED_ROLE_CODE`).

### 3-2. 조회 범위 (권한 없으면 본인만)
| 대상 | 전체 조회 조건 |
| --- | --- |
| 근태 목록·월 근태 | ADMIN or `LEAVE_APPROVE` |
| 휴가 목록·잔여일수 | ADMIN or `LEAVE_APPROVE` |
| 급여 대장·명세서 | ADMIN or HR |
| 경조비·증명서 | ADMIN or HR |

전체 급여대장·정산 엑셀은 전 직원 급여를 담으므로 **ADMIN·HR 전용**. 개인 명세서는 본인 것만.

### 3-3. 소급 등록 (`2c61afc` → `7338092` → `da935b9` → `35f6f92` → `3ae7408`)
정책이 네 차례 바뀌어 최종 형태는 다음과 같다.

| 지난 날짜 | ADMIN | HR | 일반 |
| --- | --- | --- | --- |
| 근태 등록 | 허용 | 허용 | 403 |
| 휴가 신청 | 허용 | 허용 | 400 |

병가처럼 사후 등록이 필요한 경우가 있어 관리자·인사팀만 예외로 뒀다. 종료일 < 시작일은 역할 무관 차단.

### 3-4. 명단 기준 행 생성
월 근태·월 휴가가 **기록이 있는 사람만** 행으로 만들어, 그 달에 기록이 없으면 본인 행조차 없었다. 볼 수 있는 명단을 먼저 깔고 그 위에 기록을 얹는 방식으로 변경.

## 4. 공통 기능 및 보안

### 4-1. 대리 신청 취약점 (`60fcfa2`)
`POST /leaves` 는 **메서드 인가가 아예 없었고**, 경조비·증명서와 함께 요청 본문의 `employeeId`를 그대로 신뢰했다. 로그인만 하면 누구나 타인 명의로 신청이 가능했다.

`SecurityUtils` 에 검증 유틸 추가:
```java
checkCanSubmitFor(Long targetEmployeeId, String authority)   // 휴가: LEAVE_APPROVE
checkCanSubmitFor(Long targetEmployeeId, boolean mayActForOthers)
isAdminOrHr()      // 복지: 승인 판정과 동일 기준
canActForOthers(String authority)
```
> 복지의 위임 기준으로 처음에 `EMPLOYEE_WRITE`를 썼으나, 일반직원 역할이 이미 그 권한을 갖고 있어 검사가 무력화됐다(1차 검증에서 200 확인). 승인 판정과 동일한 ADMIN/HR 기준으로 정정.

### 4-2. 급여 전면 노출 (`e1be746`)
`PAYROLL_READ`만 있으면 전 직원 급여와 **전체 급여대장 엑셀(4KB)까지 실제로 다운로드**됐다. 일반직원 역할에 해당 권한이 부여돼 있어 실사용 가능한 상태였다. `PAYROLL_READ`는 "급여 화면 사용 가능"이지 "타인 급여 조회"가 아니라고 재정의하고 범위를 좁혔다.

### 4-3. 감사로그
- 권한·공통코드 변경이 전혀 기록되지 않아 항상 0건이었다. 역할/코드의 생성·수정·활성토글·삭제를 기록.
- 행위자를 ID 대신 이름으로 표시(페이지당 1회 조회로 N+1 회피).
- `created_at`이 초 단위(`datetime`)라 같은 초에 쌓인 이력의 순서가 뒤집혔다 → id 역순 정렬.

### 4-4. 자격증명 제거 (`a2d1be7`)
`run_ssh.exp` / `run_ssh2.exp` / `deploy_expect.exp` / `run_ssh.py` 4개 파일에 대여 서버 접속 정보가 평문으로 커밋돼 있었다. `filter-branch --index-filter` 로 전체 이력에서 제거 후 강제 푸시. 코드 트리 해시는 재작성 전후 동일(`0f5aa3a`)함을 검증.

### 6-3. 발견해 함께 고친 문제
- **월 근태 격자가 `Math.random()` 으로 생성**되어 출퇴근 시각이 실제 기록과 무관했고 새로고침마다 바뀌었다 → 월 집계 응답에 `daily` 추가해 실제 기록 렌더링.
- 급여 상태 코드가 백엔드 `DRAFT/CONFIRMED/PAID` 인데 화면은 `COMPLETED/PENDING/ERROR` 를 봐서 **"정산 완료" 카드가 항상 0**이었다.
- 요약 카드 5개 호출을 `Promise.all` 로 묶어 하나만 403이어도 전체가 reject → 카드 전부 0.
- 경조비 반려 엔드포인트 자체가 없어 404(`요청한 경로를 찾을 수 없습니다`).
- 부서 색상이 `해외영업`/`마케팅` 하드코딩이라 대학 조직에 미적용 → 이름 해시 팔레트.
- 죽은 버튼 3개(발령 필터·내보내기, 급여 필터, 수당 수정) → 급여 필터·수당 수정은 구현, 발령 내보내기는 제거.
- `alert`/`confirm` 41곳 + `prompt` 1곳 → 인앱 컴포넌트로 교체.
- 로드 실패를 `console.error` 로만 삼키던 20곳 → 토스트 표시.

### 6-4. 작업 중 사고와 복구
- **정규식 일괄 치환 사고**: `alert\((.*)\);` 에 `re.S`+greedy 조합을 써서 파일의 첫 `alert(` 부터 마지막 `);` 까지 삼켰다. 컴포넌트 `return` 의 닫는 괄호가 `, "error");` 로 바뀜. 커밋 전 `git diff` 로 발견해 15개 파일 `git checkout` 복구 후, 괄호 균형을 세는 방식(문자열 리터럴 무시)으로 재작업.
- **시드 데이터 오삭제**: 테스트 정리 시 `WHERE work_date='2026-07-29' AND employee_id IN (4,5)` 로 지웠는데 박강사(id 4)의 7/29 행은 V10 시드였다. 근태 등록이 기존 행을 갱신하는 구조라 테스트가 시드를 덮어썼던 것. 생성 규칙을 재계산해 원래 값(`LATE 09:20~16:00`)으로 복구, 141건 일치 확인.

## 7. 기타/후속 연동 지점

### 7-1. 팀원 필수 조치
`main` / `backend` / `frontend` / `error` **4개 브랜치 전부 이력이 재작성**되었다. 기존 클론은 `git pull` 이 divergent 오류를 낸다.

```
git fetch --all
git reset --hard origin/<브랜치>
```

`git pull`(merge/rebase)로 진행하면 제거한 옛 커밋이 되살아난다.

### 7-2. 남은 과제
- 이번에 고친 인가 규칙(대리 신청 차단, 조회 범위, 역할 비활성)은 회귀하기 쉬운데 **자동 테스트가 없다.** 백엔드 통합 테스트로 고정 필요.
- 발령 엑셀 내보내기는 백엔드 미구현 상태로 버튼만 제거했다.
- 복지(경조비·증명서)에 전용 권한 코드가 없어 ADMIN/HR 역할로 판정 중. 권한 체계를 세분화하려면 `permission` 테이블에 항목 추가가 선행되어야 한다.
